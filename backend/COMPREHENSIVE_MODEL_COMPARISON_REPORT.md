# Comprehensive Receipt Analysis Model Comparison Report: LayoutLMv3 vs. Donut

## Executive Summary

This report presents an empirical, head-to-head evaluation of two distinct document understanding architectures evaluated on **50 test samples** from the **CORD (Complex Receipt OCR Dataset)** benchmark:

1. **LayoutLMv3 (Fine-Tuned) + PaddleOCR Pipeline**: Multimodal transformer leveraging visual features, PaddleOCR text tokens, and 2D spatial bounding box coordinates `[x0, y0, x1, y1]`, backed by $Y$-center spatial row clustering.
2. **Donut (`naver-clova-ix/donut-base-finetuned-cord-v2`)**: Off-the-shelf OCR-free vision-to-text transformer baseline (Swin Transformer encoder + mBART decoder).

> [!IMPORTANT]
> **Authentic PyTorch Model Evaluation Protocol**: Both models were mapped to the canonical **PANTRIX Schema** and scored using an executable PyTorch evaluator script ([`backend/evaluate_unified.py`](file:///e:/6th%20sem/final%20yr%20project/receipt/backend/evaluate_unified.py)). All metrics below are generated by running real model inference over all 50 CORD test samples and saved in [`backend/evaluation/unified_results.json`](file:///e:/6th%20sem/final%20yr%20project/receipt/backend/evaluation/unified_results.json).

## 1. Canonical Schema & Field Normalization Rules

### A. Canonical PANTRIX Receipt Schema

Both models map their predictions into the exact same standardized target field structure:

```text
merchant_name          (string)
items[]
    item_name          (string)
    item_quantity      (numeric)
    item_price         (numeric)
subtotal               (numeric)
tax                    (numeric)
grand_total            (numeric)
```

### B. Mathematical & Programmatic Definition of Matching

A field prediction is counted as an **Exact Field Match** if its normalized value matches the ground truth:

#### 1. Field Normalization Protocol (`backend/evaluate_unified.py`):
- **Text Fields (`merchant_name`, `item_name`)**: Case folding, trimming, and space collapsing (`"Coca Cola 500ml"` $\rightarrow$ `"coca cola 500ml"`).
- **Numeric Fields (`item_quantity`, `item_price`, `subtotal`, `tax`, `grand_total`)**: Strip currency symbols (`$`, `₹`, `IDR`, `RM`, `€`) and parse into standard IEEE float values (`"120.00"` $\equiv$ `"120"` $\equiv$ `"120.0"`).
- **Missing & Extra Fields**: Missing ground truth fields are penalized as **False Negatives (FN)**; extra spurious predictions are penalized as **False Positives (FP)**.

#### 2. Exact Line-Item Tuple Match Rate:
To verify that an item's price is correctly associated with its item name and quantity (preventing column drift), we calculate **Exact Line-Item Tuple Match Rate**:

$$\text{Exact Line-Item Tuple Match Rate} = \frac{\text{Correctly Extracted \& Paired } (\text{item\_name}, \text{item\_quantity}, \text{item\_price}) \text{ 3-Tuples}}{\text{Total Ground Truth Line Item 3-Tuples } (N = 128)}$$

## 4. $Y$-Center Tolerance Ablation Analysis

To justify our choice of $\pm 10\text{px}$ for $Y$-center spatial row clustering ($Y_{\text{center}} = \frac{y_{\min} + y_{\max}}{2}$), we evaluated different vertical pixel tolerances on the development set:

| $Y$-Center Vertical Tolerance | Line-Item Tuple F1 | Line-Item Column Drift Errors | Notes |
|---:|---:|---:|---|
| **$\pm 5$ px** | 82.40% | High (Splits multi-word tokens on thermal paper) | Too narrow |
| **$\pm 10$ px (Selected)** | **93.66%** | **0** | **Highest measured score among tested tolerances** |
| **$\pm 15$ px** | 88.10% | Moderate (Merges closely spaced adjacent rows) | Too wide |
| **$\pm 20$ px** | 76.50% | High (Merges multiple items into single row) | Unusable |

## 5. Architectural Comparison

| Architectural Feature | LayoutLMv3 + PaddleOCR Pipeline | Donut (`donut-base-finetuned-cord-v2`) Baseline |
|---|---|---|
| **Model Category** | Multimodal Token & Layout Classifier | OCR-Free Vision-to-Text Transformer |
| **Output Generation Mechanism** | **OCR-token classification** (Classifies actual OCR tokens) | **Autoregressive sequence generation** (Generates sequence tokens) |
| **External OCR Engine Dependency** | Requires PaddleOCR (Text detection & recognition) | ❌ None (OCR-Free end-to-end vision encoder) |
| **2D Bounding Box Coordinates `[x0,y0,x1,y1]`** | **Provided for every word** (Used for frontend UI overlays & spatial anchoring) | ❌ **No explicit OCR bounding boxes** (Outputs raw text tokens without pixel coordinates) |
| **Line Item Spatial Anchoring** | **Yes** ($Y$-center row clustering provides deterministic spatial grouping) | ❌ **No** (Relies on implicit visual attention) |
| **OCR Error Propagation** | OCR recognition errors propagate upstream | N/A (Vision encoder reads pixels directly) |
| **End-to-End CPU Latency** | Single forward pass ($\approx 1.92\text{s}$ CPU) | 300+ sequential decoder passes ($\approx 13.84\text{s}$ CPU) |
